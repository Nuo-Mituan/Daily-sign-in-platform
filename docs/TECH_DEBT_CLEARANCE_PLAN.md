## 1. 结论与范围决策

| 项目 | 数值 |
| --- | --- |
| 技术债总数 | 20 |
| P2 | 13 项，14.2 人日 |
| P3 | 7 项，4.6 人日 |
| 纯开发合计 | **18.8 人日** |
| 加评审/联调/回归 20% 缓冲 | **约 22.6 人日** |
| 推荐投入 | 2 名后端/平台工程师 + 1 名 QA/运维 |
| 推荐周期 | **3 个自然周**（2026-10-20 ~ 2026-11-06） |
| 单日完成 | **不可行**；直接进入 rc.2 会牺牲修复质量与回归覆盖 |

### 建议的准出范围

1. 全部 20 项必须修复并附专项测试；
2. `v1.0.0-rc.1` 仅作为技术债修复基线，不移动；
3. 全部通过后创建 `v1.0.0-rc.2`；
4. Docker 实机门禁在 rc.2 全量回归后执行；
5. 门禁通过后创建 `v1.0.0`。

如要求缩短到 **1 周**，只能将 P3（TD-14~TD-20）拆到 `v1.0.1`，P2 仍需约 2 周；这不满足当前“全部 20 项为 rc.1 阻塞项”的要求，需要重新协商准出范围。

## 5. 测试与验收

### 5.1 新增 `backend/tests/test_tech_debt_regression.py`

每一项至少包含：

- 正常路径；
- 参数/配置异常边界；
- 并发或故障注入（适用项）；
- 旧契约兼容断言。

目标：现有 **38** 项不减少；新增覆盖 20 个 TD，最终测试数 ≥ 60。

### 5.2 性能基线

涉及 TD-01/02/03/06/13 的修复，必须在修复前后记录：

| 场景 | 指标 |
| --- | --- |
| 50 并发模块输出 | 环形写 p50/p95、API p95、事件循环阻塞时长 |
| 10 万条环形日志 | append 吞吐、裁剪耗时、峰值 RSS |
| 统一批次 50 模块 | flush 总耗时、锁等待、DB 事务时长 |
| SSE 20 连接 | 首包延迟、队列丢弃数、重连补齐耗时 |

结果保存为 `docs/perf/rc2-before.json` 与 `docs/perf/rc2-after.json`；未达标不得创建 rc.2。

### 5.3 契约与兼容

- 所有 API OpenAPI 快照差异必须为空（新增内部字段仅允许可选）；
- 数据库 Schema 只允许向后兼容新增；不得重命名/删除现有列；
- 旧库升级演练：v5 库、v1 密文、旧 output、旧 push_enabled；
- 前端构建、隐私检查、浏览器回归必须通过。

### 5.4 Docker 门禁

`verify_docker.sh` 增加：

```bash
compose exec -T checkin-platform pytest backend/tests -q
```

在容器内执行全量测试（含 `test_tech_debt_regression.py`），然后执行现有 API 验证；失败即阻断。
